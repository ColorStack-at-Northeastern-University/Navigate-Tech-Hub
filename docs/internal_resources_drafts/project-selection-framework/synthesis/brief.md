KEY FINDINGS

[GEM] **Define “portfolio value” before picking the build:** a strong first-year project answers, in plain language, who it’s for, what loop they repeat, what data you store or move, and where a stranger can run or view it (README + runnable or deployed path). If you cannot state that in ~3 sentences, the idea is still fuzzy — narrow scope before writing code.

[GEM] **Scope rule:** one shipped project with a crisp README, screenshots or demo, and honest limitations beats several tutorial copies with no delta. Dev.to roadmaps consistently reward “build → break → fix” cycles; make the cycle visible in the writeup (what broke, what you cut, what you’d do next).

[GEM] **Pick a lane for depth, not a buffet:** the “20+ projects” style roadmap lists many domains; for first-year NEU pacing, translate that into **one primary lane** (e.g., small full-stack web or a focused mobile/ML slice) until you have a flagship repo you’d pin. Add a second lane only after the first has proof of integration (auth, persistence, or nontrivial logic — not only UI).

[GEM] **GitHub Education as infrastructure, not the project itself:** use the Student Developer Pack and Experiences to get Codespaces/Copilot/intro OSS pathways unblocked early so your scope budget spends weeks on features, not on paying for baseline tooling. Pair with real Git hygiene (branch, PR, issues) so the repo reads like work, not a zip dump.

[GEM] **OSS / collaboration as depth amplifier:** Intro-to-OSS-style paths (good first issues, docs, small fixes) can produce a high-trust line item faster than starting a greenfield repo from zero — especially when you document the issue, approach, and review feedback. This complements (does not replace) one owned project.

[GEM] **Fireship-adjacent takeaway:** static/portfolio tech (e.g., Astro/Hugo-class choices in Fireship’s ecosystem) can ship a professional face quickly — but treat the **product** repo (API, data model, auth, tests where appropriate) as the primary depth signal unless you are explicitly targeting frontend specialization.

[GEM] **Audience-specific UX pattern:** students in Black and Latinx tech communities often showcase **community-anchored shipping** (programs, hackathons, chapter/build weekends) with clear team roles and problem statements. Your framework should explicitly say: *document the role you owned* (which services, which endpoints, which UI surfaces), not only the group photo.

Supporting point: Dev.to “resume multiplier” lists repeat archetypes (e-commerce checkout, realtime chat, admin dashboards) — useful as **examples**, not as a mandatory checklist; choose one that matches your lane.

Supporting point: Multiple student writeups stress **writing and public artifacts** (short posts, diagrams) alongside code — low-cost scope expansion after the core ships.

DISCARDED

- “Just follow your passion” without a scope and user story.
- Choosing maximum flashy portfolio chrome (3D hero sites, heavy animation) as the first build when fundamentals (data + logic + deploy) are still shaky — high risk of time sink for first-years.
- Copying trending tutorial apps without at least one **non-template** requirement (domain twist, extra constraint, real dataset, or measurable performance goal).
- Treating community involvement as decoration only — if you name ColorStack (or similar), tie it to a **concrete artifact** (repo, demo, role, outcome).

RECOMMENDED STRUCTURE

Opening hook: You are choosing your *second* project before you have a **first** project that proves scope — so everything becomes half-finished and nothing passes the 30-second skim test.

Section 1: **What “portfolio value” means in year one** — proof of ownership, integration, and communication (README/demo), not novelty for its own sake.

Section 2: **Project selection framework** — the 3-sentence scope test; pick-one-lane rule; tutorial-plus-delta rule; when to add a second project.

Section 3: **Scope and cuts** — MVP definition, time-box, documentation checklist, honest limitations (signals maturity).

Section 4: **GitHub Education + OSS edge** — Pack/Experiences as friction removers; one OSS contribution path vs. one greenfield path (tradeoffs).

Section 5: **UX for Black/Latinx NEU first-years** — community-mediated builds (hackathons, pods), naming your role, avoiding comparison traps, aligning with campus rhythm (lighter weeks vs. crunch) without pretending everyone has the same bandwidth.

The mistake: Optimizing for **idea novelty** instead of **demonstrated scope** — recruiters and mentors can’t verify ideas; they verify repos, demos, and decisions.
