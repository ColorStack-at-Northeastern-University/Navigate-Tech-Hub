# Project Selection Framework for Portfolio Value

You pick your second portfolio idea before the first one can survive a thirty-second GitHub skim. The repo exists. The README is a default template. The “project” is really three half tutorials stitched together with nothing to say about data, auth, or what you would cut if the deadline moved up a week. That pattern reads as busy, not strong.

**Portfolio value in year one** is what a stranger can verify from your README, the runnable path or demo, and the limits you state plainly. Who is it for, what loop do they repeat, what do you store or move, and where can a stranger run it or see a demo? If you cannot answer that in about three sentences, the idea is still fuzzy. Narrow scope before you sink another night into code. One shipped project with a crisp README, screenshots or a short demo, and honest limitations beats several tutorial copies with no delta. Finishing the walkthrough is table stakes. Put what broke, what you cut, and what you would do next in the writeup so the story survives the skim.

**Use a real selection framework, not vibes.** Run the three-sentence scope test on every candidate build. Then pick **one lane** for depth until you have a flagship repo you would actually pin: small full-stack web, a focused mobile slice, or a tight ML pipeline, not a buffet. Advanced roadmaps that talk about dozens of builds are someone else’s pacing; yours is “one lane until pinned.” If you start from a tutorial, add one non-template requirement: a domain twist, a real dataset, a performance target, or an extra constraint the original never asked for. Copy-paste without a delta is a weak signal. When the lane is set, execution detail lives next door in [project scoping and execution](../../project-scoping-execution/draft/article.md) and [shipping fullstack projects](../../shipping-fullstack-projects/draft/article.md); this piece is the decision before the grind.

**Scope and cuts are part of the project.** Define the smallest shippable slice, time-box it against your real calendar (midterms and crunch weeks count), and list acceptance criteria in an issue before you romanticize stretch goals. If a feature is cool but not essential for the story you want to tell in an interview, delete it from v1. Documentation is not extra polish; it is how you pass the skim test. [Portfolio that converts](../../portfolio-that-converts/draft/article.md) is where READMEs, demos, and pins get tightened once the build exists.

**Treat tooling as infrastructure, not the project.** GitHub’s [Student Developer Pack](https://education.github.com/pack) and bundled Experiences (intro flow, pull requests, open source, Copilot, Codespaces) exist so your scope budget spends time on product work instead of fighting accounts and editor setup. The [partners](https://education.github.com/partners) page is the source of truth for which tools and perks ship with the Pack; offers change, so pull specifics from there before you lock a resume line. Pair that with real Git hygiene: branches, PRs, issues. The repo should read like work, not a zip dump. If you want depth without a greenfield app, a small OSS contribution with a documented issue, approach, and review feedback can earn trust quickly. The longer playbook sits in [open source as experience](../../open-source-as-experience/draft/article.md).

**If you ship through community programs or hackathons**, name the problem, the stack, and **the slice you owned** (which services, endpoints, and UI surfaces you touched). A group photo is nice; it is not engineering proof. Programs like ColorStack and conference-adjacent builds are strong when tied to concrete artifacts. Use [ColorStack, NSBE, and AfroTech](../../colorstack-nsbe-afrotech-guide/draft/article.md) for org-specific context and [hackathon prep](../../hackathon-prep-system/draft/article.md) when the entry is competition-shaped. Align builds with campus rhythm in plain terms (lighter weeks versus crunch); if you need Northeastern course sequencing or exam timing spelled out, pull that from [CS course planning at NEU](../../cs-course-planning-neu/draft/article.md) instead of guessing dates here.

The mistake is optimizing for idea novelty instead of demonstrated scope. Recruiters and mentors cannot verify ideas. They verify repos, demos, and decisions. In the next twenty-four hours, write a three-sentence scope brief for **one** project, delete one cool-but-nonessential feature, and open a GitHub issue whose acceptance criteria describe the smallest shippable slice.
