KEY FINDINGS

[GEM] Treat a merged PR (or a substantive merged docs/tests PR) as resume- and portfolio-grade evidence: link the PR, name the repo, one line on user impact or scope — same “show the artifact” discipline as class projects. Sources: GitHub workflow docs + CoreCV + student guides.

[GEM] Before coding: read README, CONTRIBUTING, code of conduct; comment on the issue to claim or confirm it is still available; match the project’s PR and commit conventions — reduces wasted work and reads as professional signal in thread history. Sources: GitHub Docs + Medium college guide + Dev.to guides.

[GEM] Non-code contributions count for first-years: typos, README clarity, repro steps for bugs, small tests, a11y fixes — credible when done well and easier to finish under a full course load than a feature in a foreign codebase. Sources: GitHub Docs (small fixes) + CoreCV + Dev.to.

[GEM] Discovery discipline: use labeled issues (`good first issue`, `help wanted`), curated lists (up-for-grabs, goodfirstissue.dev, awesome-for-beginners), and projects you already run locally — avoids random repo roulette. Sources: GitHub Docs + Medium + Dev.to.

[GEM] Project pick (honest first-year framing): mega-star repos often burn beginners on competition and review latency; student writeups suggest favoring maintainers who respond, clear CONTRIBUTING files, and repos in a tractable star band — still variable, so “verify maintainer activity in the last month” as a practical gate. Source: Dev.to (Pullflow et al.) — frame as heuristic, not a rule.

[GEM] GitHub profile packaging: short profile README with role keywords; pin a mix that includes at least one verifiable OSS contribution and strong class/personal projects; each pinned repo gets a README with problem, stack, how to run, and proof (screenshots or demo link where applicable). Source: Sproutern.

RECOMMENDED STRUCTURE

Opening hook: You already have class projects, but some screens reward proof you can enter an unfamiliar codebase, read norms, and land a reviewed change — without calling that “fake experience.”

Section 1: What recruiters can verify — merged PRs, issue threads, docs commits; how that complements (not replaces) project screenshots and demos.

Section 2: First contribution playbook — labels, CONTRIBUTING, comment-first etiquette, smallest shippable change; link to GitHub Docs as the procedural backbone.

Section 3: First-year honest constraints — timeboxing, maintainer silence, first PR taking longer than a weekend, normal rejection/iteration; permission to start with docs/tests.

Section 4: Profile and resume lines — pins, README template, one-line OSS bullets with links; tie to Sproutern-style student profile hygiene.

Section 5: Audience rails — ColorStack context (verified only), All In / Catalyst-style structured programs as optional bridges. [FACT CHECK block in draft.]

The mistake: Treating “I opened a PR” as portfolio signal when it is unmerged, abandoned, or unlinked — you need a review story or a merged artifact.

Close: In the next 24 hours, pick one tool you already use, find one labeled issue or docs gap, post a short comment intent, and timebox exploration to one session — ship nothing big, confirm the workflow.
