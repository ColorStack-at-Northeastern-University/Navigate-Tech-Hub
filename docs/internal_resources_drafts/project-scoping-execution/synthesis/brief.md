KEY FINDINGS

[GEM] Fix the **six-week (or your-term) timebox in calendar dates** before you sort features — without a deadline, “Must have” lists are meaningless; scope is the variable, not the end date. Sources: Stack Junkie (MoSCoW solo); aligns with draft “Week 0” spine.

[GEM] Write **one sentence “ship”** plus **explicit non-goals** (what you will not build this cycle). Practitioner one-pagers use problem / user / approach / in-scope / out-of-scope; students should keep the same artifact in Notion or README. Sources: tactical PM scoping summaries + draft scaffold.

[GEM] Use a **six-week milestone spine** tuned to student reality: Week 1 — runnable skeleton + manual demo path + deployment or deploy path stub; Weeks 2–3 — core user loop; Week 4 — **riskiest integration** (the part most likely to fail); Week 5 — hardening, bugs, minimal tests; Week 6 — README, public demo, retrospective note for interviews. Sources: draft article structure + Makebolt-style risk-first sequencing.

[GEM] Run **solo MoSCoW with bias fixes**: (1) workaround test — if users could limp without it at launch, it’s not a Must; (2) cancellation test — would you cancel the whole ship without it; (3) **Must-Haves ≤ ~60% of realistic capacity** so slippage has somewhere to go; (4) write **Won’t this timebox** explicitly so features don’t creep back at night. Source: Stack Junkie + DSDM MoSCoW framing cited there.

[GEM] **Define “done” before coding**: observable criteria in plain language; **cut the MVP twice**; park everything else on a v2 list you do not touch until v1 ships. Add **~50% buffer** to hour estimates for school-induced context switching. Source: Super Productivity.

[GEM] **Ship a thin vertical slice early** (landing + one path, or CLI published, or stub in prod) — kills “someday” psychology, surfaces deploy friction when it’s cheap, enables feedback. Source: Super Productivity (“Deploy on Day One”); fits Week 1 of the spine.

[GEM] When the schedule slips, **triage like a practitioner**: defend the core user path and correctness; cut secondary workflows and polish first; avoid “one more feature” before the demo path works end-to-end. Source: Makebolt-style buckets + student hackathon retrospectives (ruthless scope).

[GEM] **Teams (2–4 students)**: pick one **scope decider** for the six weeks; clarify **merge and deploy ownership**; keep rituals tiny (short sync + shared board). Source: draft scaffold + RACI-style PM guidance (simplified for students).

[GEM] For **audience-relevant pressure**: treat **club demos, hackathons, career fair, or sponsor sessions** as fixed milestones — same scoping rules as a product date (scope shrinks; date does not). Sources: community search (time-boxed events, org-hosted hacks) + execution guides.

Supporting point: Multiple sources converge — scope creep and perfectionism at ~80% completion kill student projects; external milestones and written non-goals are the countermeasure.

Supporting point: “Specificity is the MVP” from student failure posts — vague hardware or “full product” visions die under timebox; narrow the path and ship.

DISCARDED

- “Just be more disciplined” / “stay consistent” without timebox, written scope, or early deploy.
- Generic “dream big” without non-goals or risk ordering.
- Treating every feature as equally load-bearing (solo Must Have inflation) — addressed with explicit tests and capacity cap.
- Heavy enterprise PM ceremony (full RACI decks, multi-stakeholder workshops) — wrong register for underclassmen; keep the **ideas** (one owner, written scope) only.

RECOMMENDED STRUCTURE

Opening hook: Six weeks is plenty until the calendar fills — scope for the **weeks you actually have**, not a fantasy timeline; the article is for **students** executing like **practitioners** (clear ship, clear cuts).

Section 1: Week 0 — one-sentence ship, non-goals, and where the artifact lives (README / doc).

Section 2: The six-week milestone map — skeleton + demo path, core loop, hardest integration week, hardening, ship week (docs, deploy, retro); tie each week to a **demoable checkpoint**.

Section 3: Prioritization under a fixed timebox — MoSCoW solo fixes (60% Must cap, workaround + cancel tests, Won’t list); what to cut first when Week 4 slips.

Section 4: Execution mechanics — define done + MVP halving + estimate buffer; early thin deploy; timeboxed work blocks; solo vs tiny team (scope owner, deploy/merge).

Section 5: Done definition for recruiting — deploy, README, short demo, retrospective bullets for interviews.

The mistake: Expanding Must-Haves to 100% of the calendar and “finishing” only polish while the core path is still imaginary — or stopping at 80% because no one forced a ship.

Close: In the next 24 hours, **lock end-of-week-6 (or your demo) date**, write the **one-sentence ship** and **three non-goals**, and schedule **Week 1’s milestone** (runnable path + deploy stub).
